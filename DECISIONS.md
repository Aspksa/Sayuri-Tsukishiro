## D-005 — Local-first ядро на standard library + SQLite

- Дата: 2026-10-05.
- Статус: принято.
- Источник: прямой запрос пользователя начать профессиональное ядро, БД и веб-сайт.
- Решение: первая рабочая основа использует Python standard library, `sqlite3` и локальный HTTP-сервер без сторонних Python-пакетов.
- Причина: минимальная поверхность зависимостей, переносимость, простой bootstrap и предсказуемая диагностика.
- Безопасность: сервер в `0.1.x` привязан только к `127.0.0.1`; внешний доступ не включается без отдельной модели аутентификации и авторизации.

- Дата: 2026-10-05.
- Статус: принято.

## D-008 — Модуль «Диск Sayuri»

- Дата: 2026-10-05.
- Статус: принято.
- Источник: пользователь потребовал добавить в левое меню модуль с точным названием **«Диск Sayuri»** и развивать его как более мощное файловое пространство.
- Решение: «Диск Sayuri» является отдельным модулем `sayuri-disk` с собственной версией. Пользовательское название во всех видимых местах — строго «Диск Sayuri».
- Хранение: бинарное содержимое находится в `data/disk/objects/` под UUID; исходные имена не используются как файловые пути. Метаданные находятся в SQLite.
- Целостность: при загрузке вычисляется SHA-256; загрузка идёт потоково через временный файл и завершается атомарным переносом.
- Безопасность: имена проверяются на обход путей и управляющие символы; сервер остаётся локальным на `127.0.0.1`.
- Первая версия: папки, поиск в папке, загрузка, drag-and-drop, скачивание, удаление и статистика.
- Ограничение: корзина, версии файлов, синхронизация, паспорт документа, OCR, ИИ-анализ и семантический поиск относятся к следующим этапам и не считаются реализованными в 0.1.6.


## D-009 — Диск Sayuri 0.2 как профессиональный файловый менеджер

- Дата: 2026-10-05.
- Статус: принято.
- Источник: пользователь поручил развить Диск Sayuri до профессионального файлового менеджера и сделать рабочий макет.
- Решение: версия модуля Диск Sayuri повышается до 0.2.0. В файловый слой входят корзина и восстановление, избранное, недавние, история действий, переименование, перемещение, массовые операции, сортировки, фильтры, размеры папок, свойства и прогресс загрузки.
- Целостность: удаление папки в корзину распространяется на всё поддерево; восстановление возвращает поддерево целиком; окончательное удаление удаляет физические объекты.
- Совместимость: схема Диска 1 автоматически мигрирует в схему 2 без удаления данных.
- Конфликты: имена проверяются на уровне операций; миграция не вводит жёсткое ограничение, способное сломать старую базу с ранее допустимыми дублями.
- Дубликаты: SHA-256 используется для обнаружения совпадающего содержимого, но одинаковое содержимое не удаляется автоматически.
- Интерфейс: рабочий макет является частью веб-приложения, а не отдельной картинкой.
- Следствие: версии файлов, цифровой паспорт, предпросмотр, OCR и ИИ-анализ остаются отдельным следующим этапом DISK-003.


## D-010 — Центральный просмотр и контекстное управление Диск Sayuri

- Дата: 2026-10-05.
- Статус: принято.
- Источник: пользователь потребовал убрать историю снизу, перенести загрузку наверх, добавить правую кнопку мыши, улучшить длинные имена, иерархию папок, просмотр Office и свойства.
- Решение: файл открывается в центральном модальном окне. В нём объединены вкладки «Просмотр» и «Свойства». Правая кнопка мыши и кнопка «•••» дают одинаковое контекстное меню.
- Длинные имена: в основной таблице и центральном окне имя не обрезается до одной строки; используется перенос с полным title.
- Папки: в левой части Диска отображается отдельное дерево папок с текущей папкой.
- Форматы: браузерно поддерживаемые файлы открываются inline; DOCX/XLSX/PPTX и ODF-пакеты разбираются локально стандартной библиотекой для безопасного предпросмотра.
- Ограничение: предпросмотр Office не означает полноценное редактирование бинарного Office-документа. Редактирование содержимого будет отдельным этапом, чтобы не повреждать оригиналы.
- Приватность: предпросмотр выполняется локально и не отправляет содержимое внешним сервисам.

## D-012 — «ДНК» как глубокий профиль документа

- Дата: 2026-10-05.
- Статус: принято.
- Источник: пользователь выбрал точное название «ДНК» и потребовал изучать документ «с ног до головы», от структуры до молекул, при минимальном визуальном шуме.
- Решение: в центральном окне файла порядок вкладок фиксируется как **Просмотр → ДНК → Свойства**.
- Модель данных: ДНК хранится отдельно от оригинала в `disk_dna` и привязана к `file_id`, SHA-256, состоянию источника и версии анализатора.
- Текущий локальный слой: идентичность, целостность, структура, тип документа, молекулы с источниками, кандидаты сущностей, проверки качества и стадийность.
- Доказуемость: каждая извлечённая молекула хранит строку и фрагмент источника.
- Честная граница: без реального ИИ-провайдера Саюри не выдумывает семантические отношения, причины и противоречия; раздел «Связи» показывает ожидание семантического слоя.
- UX: ключевые показатели видны сразу, подробности скрыты в раскрываемых блоках; по умолчанию открыта только «Анатомия документа».
- Безопасность: Office/ODF разбираются локально; распаковываемый XML ограничен 16 МБ.


## D-013 — ДНК 0.4 как доказательный Evidence Engine

- Дата: 2026-10-05.
- Статус: принято.
- Источник: пользователь поручил усилить ДНК «сильнее и умнее» без добавления визуального интерфейса, затем подтвердил «Делай все».
- Решение: существующая вкладка «ДНК» сохраняется без новых визуальных блоков; развитие выполняется в анализаторе, SQLite и API.
- Факт: каждая молекула получает стабильный ID, нормализованное значение, роль, источник, evidence hash и раздельную уверенность извлечения/нормализации/доказательства.
- Эпистемика: доказанный факт и гипотеза являются разными сущностями. Локальный слой 0.4 не создаёт гипотезы автоматически.
- Профили: типы документов имеют собственные обязательные и ожидаемые поля.
- Проверки: арифметика таблиц, внутренние singleton-противоречия, quality gate, risk engine и междокументная сверка.
- Похожие документы: физический SHA-256 не смешивается с семантическим fingerprint; точный дубль, почти-дубль и связанный документ — разные состояния.
- Междокументный слой пересчитывается динамически при чтении, чтобы исправленный конфликт не оставался навсегда.
- Версии: анализы сохраняются в `disk_dna_history`; обратная связь пользователя — в `disk_dna_feedback`.
- Инкрементальность: изменение только метаданных не вызывает повторный разбор содержимого, если SHA-256 и версия анализатора совпадают.
- Память: `memory_ready` является quality gate для будущей памяти; наличие найденного факта само по себе не разрешает сохранять его как проверенное знание.
- Граф: разрешены только доказуемые ребра document→entity/action и связи дубликатов/сходства. Причинность и сложные семантические отношения без ИИ не выдумываются.
- Ограничение: OCR и реальный семантический ИИ остаются отдельными следующими слоями.


## D-014 — ДНК 0.5: внутренний интеллект без визуального шума

- Дата: 2026-10-05.
- Статус: принято.
- Источник: пользователь поручил «Делай все профессионально» после перечня внутренних улучшений ДНК.
- Решение: пользовательский интерфейс остаётся прежним; новые возможности живут в анализаторе, БД и API.
- Архитектура: базовый Evidence Engine отделён от нового `AdvancedDNAEngine`, чтобы сложные слои не превращали `dna.py` в монолит.
- Spatial evidence: реальные координаты не выдумываются. Для текста сохраняется строка; для таблиц — строка/колонка; PDF/изображения ждут OCR.
- Entity resolution: приоритет получают устойчивые идентификаторы (ИНН, VIN), а не только похожее написание.
- Обучение: одно пользовательское исправление не является глобальным правилом. Автокоррекция разрешается только после одинаковой коррекции минимум в трёх разных файлах.
- Калибровка: статистика feedback влияет на confidence только при достаточном числе примеров.
- Security: текст документа всегда является недоверенным содержимым. Найденные команды/prompt injection не исполняются.
- AI context: будущему внешнему ИИ передаётся минимальный доказательный контекст, а персональные/финансовые значения по умолчанию редактируются.
- Audit: анализы и feedback записываются в hash-chain ledger для обнаружения вмешательства.
- Package DNA: папка может иметь агрегированную ДНК без создания нового UI.
- Ограничение: отдельный background worker не включён этим решением; синхронное поведение сохраняется до самостоятельной задачи.


## D-015 — Evolution Core: эволюция только через проверяемый опыт

- Дата: 2026-10-05.
- Статус: принято.
- Источник: пользователь запросил «супер мощное эволюционное профессиональное обновление мозгов ДНК» без добавления меню.
- Решение: создать отдельный `DNAEvolutionEngine` поверх Evidence/Advanced слоёв, не превращая базовый анализатор в монолит.
- Self Review: ДНК проверяет собственные ID фактов, evidence hash, canonical value и соответствие accepted-фактов порогу уверенности.
- Regression Guard: ухудшение нового анализатора не может незаметно попасть в будущую память.
- Adaptive Profile: статистика корпуса формирует только ожидания; обязательные поля автоматически не меняются.
- Rule Lifecycle: конфликтующие коррекции не становятся активными правилами.
- Hypothesis Lab: повторная совместная встречаемость создаёт только association hypothesis; причинность запрещено выводить без отдельного доказательства.
- Global Entity Registry: каноническая сущность имеет устойчивый глобальный ID и список документных упоминаний.
- Evolution metrics: maturity score является технической метрикой проверяемого опыта, а не «процентом интеллекта», сознания или личности.
- Reanalysis planner: автоматически ничего массово не переанализирует; только выдаёт приоритетный план.
- Reanalysis cooldown: несколько одинаковых запросов за короткое окно не должны плодить версии и ledger; `deep=true` сохраняет возможность явного глубокого повтора.


## D-016 — Spatial DNA 0.7: доказуемая геометрия и локальный OCR без нового меню

- Дата: 2026-10-05.
- Статус: принято.
- Источник: пользователь запросил следующий эволюционный скачок ДНК после Evolution Core 0.6.
- Решение: пространственный слой является внутренним продолжением вкладки «ДНК», а не новым модулем UI.
- PDF backend: PDFium через `pypdfium2` с permissive-лицензированием; AGPL-зависимость PyMuPDF не закрепляется в проекте.
- OCR backend: Tesseract 5.5.3, локально, `rus+eng`.
- Координаты допустимы только из реального document/OCR engine. Никаких синтетических bbox.
- OCR confidence относится к качеству распознавания слова, а не к истинности бизнес-факта.
- Распознавание таблиц, подписей и печатей без vision/semantic слоя является только candidate/hypothesis.
- Heavy OCR ограничивается page budget и timeout для защиты локального ноутбука.
- Spatial snapshot хранится отдельно от основной ДНК.
- Optional runtime не является точкой отказа запуска приложения.
- Основной Evidence Engine остаётся единым источником молекул; OCR не создаёт параллельную систему фактов.


## D-017 — «Телефон Sayuri» как отдельный локальный модуль Android

- Дата: 2026-10-05.
- Статус: принято.
- Источник: пользователь потребовал создать меню **«Телефон Sayuri»** и подключать свой телефон к проекту для использования через Sayuri.
- Решение: модуль имеет отдельный каталог `phone/`, версию и пункт главного меню.
- Первая платформа: Android.
- Backend 0.1: официальный Genymobile scrcpy 4.1 + ADB. scrcpy выбран как Apache-2.0, локальный, без root и без обязательной установки приложения на телефон.
- Безопасность: HTTP API предоставляет только allow-listed операции device list / pair / connect / disconnect / control start / control stop. Общий adb shell не экспонируется.
- Pairing code не записывается в журнал событий.
- Управление запускается только по явному действию пользователя.
- В версии 0.1 scrcpy отображает телефон отдельным нативным окном. Форки ws-scrcpy не встраиваются из-за небезопасных по умолчанию схем без авторизации/шифрования.
- PHONE-002 должен проектировать собственный локальный streaming bridge для показа телефона внутри страницы Sayuri, не открывая управление в сеть.


## D-018 — PHONE-002: встроенное управление через локальный screenshot bridge

- Дата: 2026-10-05.
- Статус: принято.
- Источник: после успешного USB-подключения пользователь поручил перенести экран телефона внутрь проекта.
- Решение: не использовать старые сторонние web-scrcpy форки и не открывать незащищённый WebSocket control plane.
- Embedded 0.2 использует официальный ADB runtime из scrcpy:
  - `exec-out screencap -p` для кадра;

## D-019 — PHONE-002.1: disconnect является состоянием, а не потоком ошибок

- Дата: 2026-10-05.
- Статус: принято.
- Основание: реальный лог показал успешную работу embedded bridge до события `Device disconnected`, после которого UI продолжал опрашивать stale serial.
- Решение:
  - потеря ADB-authorized устройства переводит телефонный модуль в состояние disconnected;
  - stale frame/session state очищается сразу;
  - disconnect обозначается отдельным API-кодом `SAYURI-PHONE-409`;
  - клиент прекращает тяжёлый frame polling и использует редкий health/device polling до возврата телефона;
  - нативный scrcpy 60 FPS и embedded screenshot loop не должны одновременно нагружать устройство без необходимости.


## D-020 — PHONE-003: дисплей телефона является глобальным плавающим инструментом

- Дата: 2026-10-05.
- Статус: принято.
- Источник: пользователь прямо назвал прежний интерфейс неудобным и потребовал независимый дисплей, переносимый по всему проекту, с resize/rotate/mouse/keyboard.
- Решение заменяет прежнюю UX-модель PHONE-002, где экран жил внутри view телефона.
- Connection center остаётся в меню «Телефон Sayuri», но сам display/control surface находится вне view-контейнеров.
- Floating surface сохраняет layout только в локальном браузере.
- Rotation является визуальным режимом окна; input coordinates проходят обратное преобразование и остаются привязаны к реальному экрану Android.
- Keyboard input не открывает arbitrary shell:
  - системные клавиши отображаются на фиксированный список keycode;
  - text endpoint ограничивает длину и допустимые символы;
  - shell command body не принимается от клиента.
- Для высокоплавного режима остаётся официальный scrcpy.
- H.264/WebCodecs отложен до отдельного этапа после проверки нового UX на реальном устройстве.


## D-021 — PHONE-004: стабильный control/media слой отделяется от H.264 video bridge

- Дата: 2026-10-05.
- Статус: принято.
- Источник: пользователь потребовал клавиатуру ПК, хорошее качество картинки и полный набор расширений.
- Официальная документация scrcpy 4.1 подтверждает:
  - UHID является рекомендуемым режимом физической клавиатуры и поддерживает все символы/IME;
  - H.264 — основной low-latency codec;
  - recording выполняется официальным клиентом без захвата окна;
  - protocol scrcpy является internal и зависит от версии.
- Решение:
  - стабильные keyboard/file/recording/app функции выпускаются отдельной контрольной точкой;
  - H.264 browser bridge реализуется отдельным версионным адаптером строго для scrcpy 4.1;
  - отказ H.264 bridge не должен ломать PNG fallback, ADB control или нативный scrcpy;
  - пользовательский HTTP API не получает arbitrary shell.


## D-022 — PHONE-004B: H.264 browser bridge использует standalone scrcpy-server 4.1

- Дата: 2026-10-05.
- Статус: принято.
- Основание: официальный `doc/develop.md` scrcpy описывает standalone server, отдельные video/audio/control sockets, codec id, video session packet и media packet framing.
- Решение:
  - не использовать сторонние web-scrcpy форки;
  - не перехватывать SDL-окно официального клиента;
  - запускать официальный `scrcpy-server` отдельно для embedded video;
  - protocol adapter фиксируется на scrcpy `4.1`;
  - server/client version mismatch не маскируется;
  - browser transport поверх HTTP является собственным минимальным `sayuri-h264-v1`;
  - ADB forward создаётся только локально и удаляется после завершения stream;
  - H.264 control socket не используется: существующий allow-listed ADB input остаётся отдельным контуром;
  - отказ media bridge не должен ломать управление, PNG fallback или нативный scrcpy.
- Причина разделения: upstream scrcpy protocol прямо объявлен internal и может меняться между версиями.


## D-023 — PHONE-004C: clipboard и audio являются независимыми version-pinned каналами

- Дата: 2026-10-05.
- Статус: принято.
- Источник: продолжение требования пользователя о полноценной клавиатуре ПК, хорошем изображении, звуке и интеграции.
- Решение:
  - использовать только официальный scrcpy-server 4.1 и задокументированный upstream framing;
  - не использовать сторонний web-scrcpy;
  - clipboard реализовать через отдельный control-only server session;
  - audio реализовать через отдельный audio-only Opus server session;
  - video H.264, audio Opus и ADB input остаются независимыми failure domains;
  - clipboard payload ограничивается protocol maximum и UTF-8;
  - SET_CLIPBOARD требует matching ACK sequence;
  - audio никогда не стартует автоматически без пользовательского клика;
  - браузерный AudioDecoder является optional capability;
  - запуск native scrcpy должен останавливать embedded audio, чтобы исключить двойной звук.


## D-024 — PHONE-005: Companion использует ADB reverse и явное Android-разрешение

- Дата: 2026-10-05.
- Статус: принято.
- Причина: для уведомлений Android одного scrcpy/ADB screenshot/control недостаточно; нужен системный NotificationListenerService.
- Sayuri Companion является отдельным Android-приложением.
- Desktop server остаётся `127.0.0.1`; LAN listener не добавляется.
- Device → desktop transport:
  `Android 127.0.0.1:8766 → adb reverse → текущий loopback-port Sayuri`.
- Аутентификация:
  - desktop генерирует случайный token;
  - token передаётся приложению через explicit PairingActivity;
  - пользователь подтверждает pairing на телефоне;
  - Companion события требуют Bearer token и serial;
  - token не возвращается browser UI.
- Notification content не пишется в обычный журнал Sayuri; он живёт в ограниченной ephemeral queue.
- Доступ к уведомлениям выдаётся только через штатные Android Notification Listener Settings.
- APK не загружается/устанавливается до фактической CI-сборки и получения проверяемого digest.

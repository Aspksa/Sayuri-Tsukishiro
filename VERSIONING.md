# Версии проекта и модулей

Правило пользователя от 2026-10-05: каждое изменение проекта и каждого затронутого модуля должно иметь новый номер, сохранённый в локальных файлах проекта.

## Где находится версия

| Объект | Источник номера |
| --- | --- |
| Весь проект | [VERSION](VERSION) в корне |
| Служебный модуль dev-tools | [scripts/VERSION](scripts/VERSION) |
| Будущий прикладной модуль | `VERSION` в корне его собственной папки |
| Список модулей и путей | [MODULES.json](MODULES.json), без дублирования номеров |

`scripts` содержит реальные инструменты разработки. Прикладные модули чата, памяти и интерфейса ещё не созданы; не добавлять им вымышленные версии.

Версии хранятся в репозитории обычным текстом и входят в скачанный ZIP. После обновления локальной копии файлы содержат номера этой ревизии. Уже скачанная папка сама не обновляется: нужен Git pull или замена файлами новой версии. Имена папок менять при повышении версии не требуется.

## Когда повышать номер

- Любой коммит с изменением файлов повышает общую версию: код, дизайн, документация, настройки, тесты, зависимости, CI, исправления и удаление файлов.
- Изменение внутри зарегистрированного модуля повышает также версию этого модуля. Неизменённые модули сохраняют номера.
- Перенос файла между модулями повышает версии обоих модулей.
- Изменение общего компонента может затронуть зависимый модуль вне изменённых путей. Такой модуль явно добавляют через `bump --module ID`.
- Новый модуль получает начальную версию `0.1.0` и запись в `MODULES.json`. Его первое добавление повышает проект; сама начальная версия модуля дополнительно не увеличивается.
- Версия повышается один раз на сохраняемый набор изменений/коммит. Каждое нажатие клавиши или промежуточное сохранение редактора отдельной версии не требует. При следующем коммите номер снова должен вырасти.
- Все связанные правки, версии и журнал сохраняются одним коммитом. Изменения только файлов версии не порождают бесконечную цепочку новых повышений.
- Нельзя уменьшать номер. После отмены функциональности создаётся новая версия с описанием отката; прежний номер повторно не используется.
- Версия исходников не равна GitHub Release. Теги и релизы создаются отдельно по задаче, не при каждом исправлении.

## Формат

В файле `VERSION` — только `MAJOR.MINOR.PATCH` и перевод строки, без префикса `v`.

Обычное изменение: `0.1.1 → 0.1.2`. Автоматическая команда повышает PATCH. Осознанный переход этапа может повысить MINOR (`0.1.9 → 0.2.0`), несовместимый большой переход — MAJOR (`0.9.9 → 1.0.0`). Такой переход записывают в решениях и журнале; проверка принимает любой строго больший корректный номер.

Начальная зафиксированная версия всего проекта при введении этого правила — `0.1.1`; прежнее `0.1.0 «Пробуждение»` было предложением. История до введения правила не переписывается.

## Команды

Нужен Python 3.10 или новее. Для `bump` и `check` также нужен Git и локальная Git-копия. Дополнительные Python-пакеты не требуются.

Из корня проекта:

```sh
python scripts/versioning.py show
python scripts/versioning.py bump
python scripts/versioning.py check
```

На Linux при необходимости используйте `python3` вместо `python`.

- `show` выводит версии в JSON непосредственно из файлов; работает и в ZIP без Git.
- `bump` сравнивает рабочие файлы с HEAD, учитывает подготовленные, неподготовленные и новые неигнорируемые файлы, повышает проект и изменённые модули.
- Повторный `bump` относительно того же HEAD сохраняет уже повышенные номера.
- `check` завершается с кодом 1 при изменениях без повышения, неверном формате, снижении версии или отсутствии обязательного файла.
- Указанный явно зависимый модуль: `python scripts/versioning.py bump --module dev-tools`.
- Проверка опубликованного набора коммитов: `python scripts/versioning.py check --base BASE_SHA --target HEAD_SHA --each-commit`. Замените обозначения реальными SHA.

Перед коммитом проверь `git status`, внеси изменения, выполни `bump`, обнови журнал и контрольную точку, затем выполни `check`. Добавляй в коммит только файлы своей задачи вместе с соответствующими `VERSION`. Если в рабочей папке есть чужие изменения, сначала изолируй свою задачу: команда анализирует всю рабочую копию.

При работе через GitHub API обнови номера по исходной ревизии и запиши их одним коммитом с изменениями; проверь сохранённые значения и результат CI. Если ветка успела измениться, пересчитай версии относительно нового основания.

## Как добавить модуль

1. Создать настоящую папку модуля и его содержимое.
2. Добавить в неё файл `VERSION` с `0.1.0`.
3. Добавить в массив `modules` файла `MODULES.json` объект с уникальным `id` и относительным `path`. Например, для реально созданного чата: `{"id":"chat","path":"modules/chat"}`.
4. Обновить карту проекта, общую версию и журнал; выполнить проверку.

Пути не должны выходить из проекта. Нельзя просто убрать модуль из реестра, оставив его файлы: проверка отклонит это. Удаление самого модуля фиксируется в журнале и повышает версию проекта.

## Автоматическая проверка в GitHub

[versions.yml](.github/workflows/versions.yml) запускает тесты инструмента и проверку версий на push и pull request без исключения документации. В проверяемом диапазоне проверяется каждый коммит основной линии его истории, а не только итоговая разница.

Workflow проверяет номера, но не создаёт коммиты и не повышает их за разработчика. При ошибке он завершается неуспешно. Обязательный запрет слияния требует отдельной настройки защиты ветки; эта задача такую настройку не меняет. Для нового ответвления без предыдущего SHA проверяется последний коммит, для самого первого коммита — корректность введённых версий.

## Когда появится приложение

Интерфейс, диагностика и локальный отчёт должны читать общую и модульные версии из этих источников или формируемых при сборке метаданных. Нельзя держать независимые вручную набранные номера в нескольких компонентах. Для будущих package-манифестов добавить синхронизацию и проверку до их использования.
